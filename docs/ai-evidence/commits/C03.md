## 2. Objective

**Objective:** Provide secure organization-scoped login, revocable credential sessions, authenticated identity, and backend-enforced ADMIN authorization for the C04 asset foundation.

**Research/engineering question:** How can DefenSME authenticate tenant-scoped users, rotate/revoke credentials, and enforce roles without exposing account existence, storing raw tokens, or moving authorization authority to the frontend?

**Acceptance checkpoint:** A valid active user can log in and access `/me`; wrong, unknown, disabled, missing, expired, rotated, or revoked credentials fail safely; an ADMIN can list only users in the authenticated organization; an ANALYST is denied; all authentication and PostgreSQL migration tests pass.

## 3. Context classification

### Confirmed facts

- C03 requires login, adaptive password hashing, token/session handling, Spring Security, and authorization tests.
- User emails are unique only within an organization, so login requires organization context.
- Spring Boot is the authentication and authorization authority; the frontend is not a security boundary.
- The approved roles are `ADMIN`, `IT_MANAGER`, `ANALYST`, and `VIEWER`; authorization is deny-by-default.
- Disabled users cannot authenticate or refresh sessions.
- Authentication errors must not reveal whether an email exists, and audit records must not contain credentials or tokens.

### Assumptions

- `[ASSUMPTION]` A 15-minute access token and seven-day refresh session are suitable initial course-project defaults and remain environment-configurable.
- `[ASSUMPTION]` The client can provide `organizationId` at login until a stable organization slug/discovery flow is approved.
- `[ASSUMPTION]` Immediate access-token invalidation is preferred over stateless-only JWT logout, so every authenticated request validates its session identifier.

### Open questions

- `[OPEN QUESTION]` Organization slug/login discovery and account recovery are not defined in PRD v1.0.
- `[OPEN QUESTION]` Production key rotation, multiple signing keys, and device/session management require deployment requirements beyond the MVP.
- `[OPEN QUESTION]` OQ-04 remains unresolved for CRITICAL AI review and is not decided by C03.

## 9. Corrections and rejected suggestions

- **Corrected:** changed refresh-token persistence from raw values to SHA-256 hashes and used a cryptographically secure 256-bit random token.
- **Corrected:** tied each JWT to an active server-side session so refresh rotation and logout invalidate access immediately.
- **Corrected:** authentication audit writes use an independent transaction so failed-login events are not rolled back with the failed authentication operation.
- **Rejected:** a global email-only login because C02 defines email uniqueness within an organization rather than globally.
- **Rejected:** a stateless JWT-only logout because it cannot revoke an already issued token immediately.
- **Rejected:** returning different messages for unknown, disabled, and wrong-password accounts because that enables account enumeration.
- **Rejected:** implementing user creation, reset, MFA, or assets in C03 because they exceed the planned checkpoint.
- **Failed attempt:** the first pull-request CI run failed compilation because `spring-security-oauth2-jose` supplies JWT primitives but not the resource-server authentication classes, and `JwtAuthenticationToken` was imported from the JWT package. The correction added `spring-boot-starter-oauth2-resource-server` and used `org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationToken`; the repeated CI run passed.
- **Failed attempt:** the first remote update carrying that correction constructed malformed Git tree paths while encoding multiple files, so checkout failed before any project command ran. The branch tree was rebuilt from the verified C02 base with explicit path/blob entries and CI was rerun; this was a repository-transfer failure, not an application test failure.
- **Failed attempt:** the next Java compilation exposed generic invariance in the JWT authority converter: `List<SimpleGrantedAuthority>` could not satisfy `Collection<GrantedAuthority>`. The stream mapping was explicitly typed as `GrantedAuthority`, after which compilation advanced to the integration suite.
- **Failed attempt:** the first integration run reached all eight tests but reported five errors: PostgreSQL JDBC could not infer a SQL type for `Instant` in the native audit insert, and the isolated health-controller test loaded the auth advice without its `Clock` bean. Audit timestamps were bound as `java.sql.Timestamp`, while the health slice excluded unrelated auth advice and security filters; the full integration suite still tests the real security chain.
- **Local tooling limitation:** local Maven execution remained unavailable because the workspace has Java 17 and no Maven executable while the project requires Java 21. The Java 21 GitHub Actions runner executed the full acceptance suite without reducing the target runtime.
