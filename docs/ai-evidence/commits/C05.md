## 2. Objective

**Objective:** Provide a responsive React workspace in which authenticated users can find and inspect organization assets, while authorized staff can create, update, and archive them through the verified C04 API.

**Engineering question:** How can the first operational DefenSME frontend expose the complete asset workflow clearly without duplicating backend authorization or permitting tenant context to be selected in asset requests?

**Acceptance checkpoint:** The application builds and lints; login establishes an authenticated session; list, search, filters, pagination, detail, create, edit, and role-appropriate archive actions call the C04 contracts; loading, empty, validation, success, authorization, and API failure states are represented.

## 3. Context classification

### Confirmed facts

- C05 requires asset list, create/edit/detail, search/filter/pagination, and validation states working through persistence.
- C04 accepts no asset `organizationId`; tenant scope and authorization come from the validated access token.
- All roles can read; `IT_MANAGER` and `ANALYST` can create/update; only `IT_MANAGER` can archive under the approved detailed RBAC matrix.
- `ARCHIVED` is reached only through the archive action and archived assets cannot be edited.
- The existing frontend is a minimal React 19/Vite shell without routing, an authentication screen, or a component test framework.

### Assumptions

- `[ASSUMPTION]` A single authenticated asset workspace and side-panel create/detail/edit flow is sufficient before broader routing is introduced with later modules.
- `[ASSUMPTION]` Session storage is suitable for the current course-project browser session; refresh orchestration and hardened browser credential storage require a later security decision.
- `[ASSUMPTION]` Metadata can be edited as bounded JSON until asset-type-specific fields are defined.

### Open questions

- `[OPEN QUESTION]` The product has no approved organization discovery/slug flow, so login continues to require the C03 `organizationId` contract.
- `[OPEN QUESTION]` User lookup for owner selection is not available to IT_MANAGER/ANALYST in C03, so C05 accepts an optional owner UUID rather than an invented user-search API.
- `[OPEN QUESTION]` Client-side refresh-token rotation and multi-tab session synchronization are not scheduled explicitly and require security design before implementation.

## 9. Corrections and rejected suggestions

- **Corrected:** removed `ARCHIVED` from the normal update selector and made archive a separately confirmed action shown only to IT_MANAGER.
- **Corrected:** every filter and page-size change resets the page to zero so stale page indexes do not produce misleading empty results.
- **Corrected:** asset payloads never contain organization context; only the bearer session supplies it to the backend.
- **Rejected:** treating hidden buttons as authorization because backend method security is the actual boundary.
- **Rejected:** adding an owner dropdown backed by the ADMIN-only `/users` endpoint because ANALYST and IT_MANAGER would not be authorized to populate it.
- **Rejected:** adding a router, component library, icon package, or state framework for a single bounded workspace without demonstrated need.
- **Rejected:** implementing C06 demo accounts/data and expanded automated test infrastructure inside C05.
